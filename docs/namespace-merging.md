# Adjacent namespace cleanup

`--merge-namespaces` (JSON `"mergeNamespaces": true`, Action input `merge-namespaces: true`) enables optional final-text cleanup. It defaults off. `--no-merge-namespaces` overrides JSON configuration.

The cleanup runs after optional include hoisting and documentation metadata removal, before blank-line collapse. Both lightweight generation and compiler-backed stitching use the same renderer, including baseline/trial/final validation and byte reports. A stitched baseline already contains this cleanup; stitching validation does not independently prove the cleanup equivalent to the original unmerged source.

Ordinary single-component named namespace definitions merge only when their closing/opening tokens are adjacent apart from whitespace or comments, have the same literal name, and occupy the same parsed parent scope. Declarations retain their order. Comments, including licenses and namespace labels, retain their bytes. A cached token adjacency queue processes newly exposed child boundaries until no more can be removed, so merging outer scopes exposes nested sibling merges at arbitrary depth. The source is structurally scanned once; no fixed pass count or repeated whole-file reparsing is used.

Compact C++17 `namespace a::b`, anonymous namespaces, inline namespaces, attributed namespace definitions, and namespace aliases remain unchanged. The pass does not move declarations across other declarations or preprocessor directives between the closing/opening namespace tokens. Internal conditionals are allowed when branches retain their enclosing namespace scopes; conditional function/control-flow braces and pragmas do not disqualify a namespace. Includes inside a body remain a barrier because an unexpanded header can alter its scope structure. Literal strings, raw strings, character literals, digit separators, comments, line splices, and alternative brace tokens are lexed structurally rather than matched by regular expression.

## Macro limitations

This is a conservative text transformation, not a preprocessor or a C++ equivalence proof. Enable it only after checking the project's macro conventions, including macros supplied through external headers and compiler arguments. Arbitrary externally defined macros cannot be inferred from the assembled text and may change namespace names or generate braces even at an ordinary declaration position. Lowercase external declaration macros are a particular unsupported case. An opt-in cannot substitute for that review.

Known macro definitions are considered across the assembled text, including conditional/later redefinitions. Uses of macros whose replacement contains braces, namespace tokens, or token-pasting operators prevent merging enclosing blocks, as do aliases to such macros. Function-like macros are allowed unless their expansion or arguments can change that structure. Names are not classified as macros based on capitalization, declaration position, or call syntax. Uppercase enum constants, template parameters, ordinary function calls, and annotation macros do not disqualify namespaces. Namespace names referring to locally defined macros remain unresolved, and a locally defined macro named `namespace` disables the pass because removing a namespace header would also remove its expansion.

Macros supplied only by external headers or compiler flags are not inferred from identifier spelling. Those definitions must be available in the assembled text if they affect namespace/brace structure. Namespace merging is a structural cleanup with these preprocessing limits, not a compiler equivalence check. Removing lines can also change source-location observations, as with other formatting cleanup.
